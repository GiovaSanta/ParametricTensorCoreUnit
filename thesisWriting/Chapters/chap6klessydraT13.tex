\section{Integration Objective and RISC-V Klessydra T13 Core Context}

%in this section, goal is to explain the context + the objective not yet the detailed RTL.

% goal of the section is to explain why the Klessydra Integration is different from the FlexGrip Plus gpu architecture.

%in this section, the reader should understand what environment im integrating into, Why Klessydra is different target from the FLexGrip Plus, Why the TCU maps naturally to a 16-hart configuration. What the integration objective was. What high-level architectural choice I made.

The integration target focused in this chapter is different then the one described in chapter 5. In fact, the Klessydra T13 RISC-V core is not a GPU inspired architecture like the FLexGrip Plus. More spcifically, unlike the FlexGrip Plus which was a GPU warp oriented architecture containing many cores for thredas to execute in parallel, the Klessydra T13 core is a RISC-V multi-hart core environment. This means that this core is able to execute the program at hand with the help of multiple harts but by using different scheduling mechanisms. Very differently from the GPU, in most cases the harts dont utilize a inner unit all at once in parallel like it was possible in the FLexGrip Plus, but they are scheduled by means of a counter in round robin fashion sequentially. Each of the hart waits its turn to be scheduled in order to occupy a inner execution unit of the core. Hence, the existance of this different topology gives a different validation and integration approach of the TCU inside the core with respect to the integration performed in the FlexGrip Plus. Overall the objective of this integration was to evaluate the parametric TCU in a processor-oriented RISC-V environment rather than only in the GPU-style FLexGrip Plus execution flow.

%paragraph2. Explain the 16-hart/single-wrapper match

In the FLexGrip Plus integration work, the design problem was adapting a 32-thread warp executor to a 16-lane TCU. And like discussed in the previous chapter, this problem had been tackled by constructing a TCU wrapper which contained 2 instances of the parametric TCU. In the Klessydra T13 Core the problem at hand is a bit different. This type of Klessydra Core in fact normally executes at most through the help of 3 harts. However, when building the RTL processor through cmake, the configuration file allows to build the RTL supporting a maximum 16 harts. Hence, in this integration work a single parametric TCU has been instantiated in a Klessydra T13 core with a configuration based on 16 harts.

%paragraph 3: Stating the real integration objective. ---> the objective was not only to instante the TCU. it was to make it usable from the Klessydra pipeline.

The integration objective was not only to instantiate the single instance of the parametric TCU inside Klessydra, but it involved also that to perform additional RTL design work to make the accelerator usable through HMMA instruciton execution. The additional design work involved that of understanding how the core can recognzize the HMMA instruction, in which sections to instantiate the accelerator, additional controls and buffers before of the actual accelerator's execution, and other related decisions.

The starting version of the Klessydra core has inner components arranged so that they follow a four staged pipeline execution involving fetch, decode, execute and write back while executing an instruction. Instead of instantiating the TCU accelerator inside the component related to the instruction execute component, it has been decided to instantiate it as its own seperate branch. Doing so, the TCU component branch receives a request from decode and manages write back and execute separetly.

\section{Custom HMMA Instruction Encoding and Decode Path}

Just like explained in the integration work related to the FlexGrip Plus GPU, the instantiated TCU in the integration of the Klessydra Core has to be executed through the related HMMA instruction. Hence, it was important to come up with a proper encoding structure for the HMMA instruction related to the Klessydra T13 core to target the parametric TCU. Like the structure of the HMMA instruction of chapter 5, the instruction needs to carry information regarding the operand register indices, the HMMA step, and the numerical format type chosen along with the bit width of operands. 

%paragraph2 : explaining the encoding figure. 

The instruction designed follows the RISC-V taxonomy utilized for the general instructions of the instruction set architecture of RISC-V. This implies that it contains the operation code for understanding that the type of instruction's intended operation. It also involves bits for the constainment of information regarding which registers contain the source operands of the instruction along with the destination register for which the instruction's result is saved. Lastly, very importantly, there is the space in the instruction for the 'funct7' and 'funct3' fields. These fields are used in the RISC-V's taxonomy to have more information regarding the execution of the instruction. For instance for an ALU instruction, RISC-V may use the funct7 bits to understand the type of logical operation. In the case of the HMMA instruction of focus, these bit fields have become important to distinguish which numerical type the parametric TCU needs to focus on and which width are the operands. While the understanding whether the HMMA instruction is of type step 0 or step 1 is done through the decoding of the lower significant bit in the funct3 bit field. 

Figure~\ref{fig:klessydra_hmma_encoding} shows the custom HMMA instruction
encoding used for the Klessydra integration. The Figure showcases which bit indexes of the instruction are dedicated to the previously introduced fields. An interesting remark to notice with respect to the HMMA instruction structure of the FlexGrip Plus is that the third source operand used for the accumulation is defined in the same field as the destination register. This was done due to the space limitations of the 32 bit wide instruction and also for program comodity since hmma instructions of various sets fetch the result obtained by previous hmma instruction for accumulation to eventually reach the final result of the bigger matrix. Along with the bit indexes the Figure showcases also the example of the content of an hmma step 0 instruction involving the fixed point 16 format operands.

With regards to the HMMA instruction, changes have been made in the decode stage related RTL component of the core as well. The changes make it so that the accelerator's support is enabled for the later execution. There is a check in the decode unit regarding the funct7 and funct3 bits of the hmma instruction (whether funct7 bits correspond to a supported TCU numerical format). If the check is passed, a valid signal is asserted on by the decode unit which enable the TCU to perform the related accelerator work in the execution stage.

Along with the valid signal, the Decode stage also recieves a related busy TCU related signal. This is an input for stall behavior in the decode circuit. In fact, while the TCU instruction executes in order to avoid out of order behavior by the core and avoid hazards, the stall by the decode may be raised in order to make the TCU finish its operation before performing work related to new assembly instructions. 

\section{Dedicated TCU Branch Integration in the Processing Pipeline}

%This section should explain the top level pipeline integration, not yet the internal details of the TCU_Branch module. goal is also to explain where the TCU branch is placed in klessydra T13 pipeline and why this is an architectural branch and not just a modification inside the ie_Stage component.

After the custom HMMA instruction is recognized by the decode stage, the
operation must be forwarded to a hardware block capable of executing the
tensor operation. In this implementation, the tensor core was not inserted directly inside the
standard instruction execution stage. Instead, a dedicated TCU branch was added at the processing-pipeline level.

%paragraph2: explain the pipeline-level modification

In regards to the execution related components which were altrady found in the core which are on branches parallel to the TCU component, they are ones related to different types of instructions which the core already supports. For instance, there is the Load and Store Unit (LSU) which is executed by the harts when load or store instructions reach the execute stage. There is also the multi functional unit (MFU) which has its own branch and is an accelerator for higher precision mathematical instructions. Lastly in the execute there is the branch related to the general instruction execute, the IE STAGE component, which deals with most of the instructions such as the ones requireing the use of the arithmetic unit. Consequently, the parametric TCU has been placed on its own separate branch outside of the involvement of these already existing units. 

The Figure~\ref{fig:klessydra_t13_tcu_pipeline} shows the version of the klessidra core in which the TCU was integrated on. This Figure portrays the various units utilized in the pipeline of the Klessydra T13 core from the fetch down to the write back stage related components. The Figure displays the design decision previously introduced: the TCU is integrated in its own separate environment in a different branch with respect to the other components composing the execute stage of the core.

Regarding the interface of the TCU, it receives signals from the register files associated to the harts for operand collecting. It also is receiveing signals from the decode related RTL component of the core for the request of starting of the accelerator's operation due to the recognition of an HMMA instruction along with communication to it to make the decode stall in the case the TCU is busy executing. Lastly, it also sends information for writing back the results to the register file once all the harts finish the related HMMA instruction on the TCU hardware.

\section{Internal Organization of the TCU Branch}

%this section talks about how the tcu wrapper works internally in klessydra in order for the tcu accelerator to be integrated properly and function as expected.

The previous section showed in high level terms where the parametric TCU is placed with respect to the pipeline of the Klessydra process. This section goes more in detail by explaining what is found inside the hardware branch which leads to the TCU. Furthermore, additional components have been introduced inside this wrapper with respect to the wrapper utilized during the FlexGrip Plus' TCU integration work. This is because the TCU itself is an accelerator which is design for GPU architecture rather then CPU's like the Klessydra one in this study. Nonetheless, with the proper wrapper RTL description the TCU accelerator is also able to function in this different target environment. The wrapper containing the parametric TCU's hardware handles instruction capture, staging of the openrands, execution of the accelerator, result capture and the writeback interface to the register files of the harts. To manage all these, there is also inside the wrapper an additional control FSM managing the execution with more organization.

Figure~\ref{fig:klessydra_tcu_branch_internal} shows the internal organization of the dedicated TCU branch. The diagram highlights the main logic blocks used
to connect the Klessydra pipeline interface to the parametric TCU and to the register-file write-back path.

\subsection{Instruction Capture and Format Selection}

The wrapper circuit receives an already accepted verified HMMA instruction from the RTL description of the decode stage of the core. At the same clock cycle of the decode stage, it extracts the relevant R-type fields for a given hart. Rs1, Rs2 and Rd identify the related operand/result registers which are involved. funct3 identifies the HMMA step, and funct3 identifes the numerical format/type. 

\subsection{Operand Collection and Lane Staging}

The Klessydra core exposes operands through the hart's register file context similarly to the FlexGrip Plus. Also, it is important to remind that the TCU instantiated inside the wrapper module expects lane-organize input vectors. For each of the scheduled harts, one at a time they will obtain the operands from the register file and feed them to operand collection Buffers. This is because as explained previously, the harts are not fetching the operands from the registers all in parallel, but are scheduled sequentially one after another as a paradigm of the Klessydra core. This leads to say that the process of TCU operand collecting from the register files is a slower with respect to the equivalent procedure done in the FlexGrip Plus. 

\subsection{Controller FSM and Tensor-Core Wrapper Execution}

For the overall TCU execution in the Klessydra T13 core, the FSM controller unit is defined inside the wrapper as well. It controls the execution from the procedure described in the previous subsection related to the operand collection phase from the register files of the harts to the staging buffers, down to the write back related control for giving the results to the register files of the harts. For the operand collection phase, the controller is necessary because by means of internal signals it can understand when all harts are done with the operand collection so that they can move to the next state which is that of launching the instantiated TCU module. This avoids the wrong behavior of making a hart which is done collecting operands launch the TCU calculation while the other harts are not yet done collecting their own operands. Also this controller FSM unit is the one which is able to signal to the previous decode stage unit of the pipeline the need for stalling as soon as the TCU wrapper is operating through the means of a busy signal. While the internal instantiated parametric TCU is launched and performs its work as described in detail in chapter 4, the controller FSM found in the Klessydra TCU wrapper puts its harts in a wait state, waiting to be woken up by the parametric TCU in order to finish the operation in the write back phase. As soon as the parametric TCU is done performing its work related to the HMMA instruction since it is constructed to live inside a GPU architecture, it gives all the results related to all the harts in a single time. To not loose itsvalues then, these results are placed in result buffers each one for a related hart. The scheduled harts then take turns in round robin fashion in writing the repsctive result to the destination register of the related hart register file. After the last operation, the HMMA operation thanks to this outside controller unit is finished and the busy signal is zeroed to let the core understand that the execution of the next instruction of the program can continue.
