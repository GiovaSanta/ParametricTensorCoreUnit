\chapter{Experimental Evaluation}

\section{Chapter Overview}

%main message: this chaper moves from architecture and integration to quantitive evaluation.

After the implementation of the architectural parametric DPUs and TCU and the related work regarding the integration of the accelerator inside the FlexGrip Plus and the Klessydra T13 core, an experimental evaluation targeting the accelerator has been performed, and discussed in this chapter.

The evaluation is done from several point of view: hardware cost, timing/performance, numerical accuracy and resiliency/fault behavior. These qualities are compared among the different numerical formats which are supported in the TCU accelerator. Equivalently this means that the metrics are obtained for the various DPUs inside the TCU. This is because the DPU and its dot-product/MAC operation is the basic main computational unit used inside the TCU. 

This chapter will portray the results obtain in regards to the metrics mentioned along with providing a detail discussion relating to the obtained numerical results. In the next section, the relative experimental setup is explained for obtaining the metrics regarding the implemented RTL-level descriptions implemented in the thesis.

\section{Experimental Setup}

%purpose of this section is to describe what was evaluated and how. 

As explained in detail in chapter 3, the numerical formats supported in this work for the parametric TCU to handle regard the FP8, FP16, FP32, Posit8, Posit16, Posit32, LNS16, INT8, INT16, FixedPoint8, FixedPoint16 numerical formats. Additionally, as explained in the background in chapter 2, the TCU accelerator performs the matrix multiply operation thanks to inner parametric DPUs which are implemented with a combination of DPUs each supporting specific numerical formats. In this thesis work it was decided to focus on the DPU level metrics to understand how the different internal DPUs distinguish themselves in terms of hardware area, performance, and resilience. Hence the experimental setup described in this work regards the granular level DPUs found inside the TCU accelerator. This decision has been made to decrease the synthesis related and fault resilient timings that are necessary to obtain the results. Henceforth, the results regarding resiliancy performance and synthesis related to the whole FlexGrip Plus GPU unit with the additional TCU and Klessydra Core unit with its own TCU are to be done in a future work, even though the performance is mentioned briefly at the end of this chapter.

Regarding the DPU related tests done for the obtainement of the numerical results regarding the various formats, the Vivado Simulation and Synthesis Tools have been utilized. The synthesis tool has been utilized for the calculation of the slack metric related to the singular DPU for the calculation of the performance of the DPUs for each of the formats. Furthermore, the synthesis process has also been performed for each of teh DPUs for the objective of obtaining how much gate level area each of the DPUs occupy. During the synthsis of the DPUs, it was decided to use the Vivado synthesis using the AMD/Xilinx Artix-7 FPGA as target device. 

Regarding the results obtained relating to the numerical accuracy for each of the DPUs of the formats, the Vivado simulation tool has been utilized confronting the simulated behavior of a specific numerical DPU with respect to the expected result. Similarly, for the analysis of the resiliency of each format, the same Vivado Simulation tool has been utilized. So this proves that both the synthesis and simulation related processes are needed for the discorvery of the metrics. Both tolls have been utilized in conjunction with various TCL scripts for launching the synthesis or simulation with the additional support of Python scripts for the generation of many random tests for the DPU used for instance when calculating the numerical accuracy of each target DPU. 

\section{DPU Level Hardware Utilization Analysis}

%This section should answer how expensive is each numerical format in hardware.
%how fast is each implementation.

%Paragraph 2: Explaining the resource metrics and what they mean: LUTs, FFs, DSPs, BRAMs.

For the results obtained regarding the hardware utilization and timing, the synthesis tool has been utilized. Each DPU targeting a different format has been synthesized independently from the others. In regards to the analysis of the area hardware required for each of the DPUs, after the synthesis is complete, Vivado generated a resource related report with information regarding the area required and other information regarding digital occupancy expressed through various resource metrics. Regarding the area resource metrics, the synthesis report gave  information about different area related metrics for the synthesized DPU: 
\begin{itemize} 
    \item  \textbf{Look Up Tables (LUTs)}: they are the basic blocks used to implement combinational logic. When the DPU of target in the synthesis needs adders, comparators, multiplexers format decoders and others, the synthesis shows this information through the LUT area metric.
    \item \textbf{Flip Flops (FFs)}: sequential storage elements used for registers, pipeline stages and intermediate signals.
    \item \textbf{Digital Signal Processing block (DSP)}: dedicated arithmetic resources in the FPGA fabric. They are mainly used for the multiplication and multiply-accumulate operation when the synthesis tool maps the target datapath to them.
    \item \textbf{Block Random Access Memory (BRAM)}: Block RAMs are dedicated on-chip memory resources. They are mainly used for buffers, memories, and large lookup tables.
\end{itemize}

The resource usage changes significantly depending on the format. In general as remarked by the previous table, for the dot product operation regarding the numerical formats with higher bit widths there is more hardware required. For instance as remarked in the table, the LUTs needed for FP32 format are about twice as much then the ones needed for the DPU which targets the FP16 format. This is effect is shown for all the formats. In fact as observed in the Table, also the Posit format is made of DPU which requires more LUT elements when the posit numerical format has width of 32 bits. The reason for this result is trivial and it is because larger operands require wider embedded adders, multipliers , normalization logic and more internal signals in their respective DPU level hardware organization. 

Another remark which can be made related to the areas of the DPUs regarding the various formats is that the posit formats usually have higher LUT usage than the corresponding floating point formats. In fact for the synthesized DPUs, the DPU which supports Posit 32 width elements has 1112 LUT elements more with respect to the FP32 synthesized DPU. This is due to the fact that Posit related DPUs involve more additional combinatorial circuits with respect to their floating point counter parts due to the needed regime decoding and the fact that it is a format witch excpects the regime filled of variable length like described in chapter 2. Basically, the Table suggests a trade off with the flexibility and area of implementation since the Posit rapresentation introduces additional decoding logic. 

Another interesting result displayed by the Table regards the LNS16 format compatible DPU. In fact it is seen that this DPU has a number of LUTs which is comparable to the amount of LUTs utilized for the FP32. This indicates how hardware expensive the LNS16 DPU is, as its LUT count is comparable to that of a DPU supporting elements of higher precision. The reason for this negative mismatch is due to the idea that the LNS16 DPU's inner addition modules are a lot more complex then the other embedded addition related to the other available as anticipated in chapter 2.

Regarding the DPUs which support the Integer and Fixed Point formats, their simplistic RTL-description is convayed in the Table as for these formats there are less LUTs required with respect to the formats described previously. Also, interestingly the synthesis tool of Vivado maps very few LUTs for the INT16 related DPU, but this is due to the fact that it maps the synthesized model into an increased count of the DSPs instead.

Regarding the BRAM resource metric, the synthesis tool has mapped 0 BRAMs for each of the DPUs of the formats because they are isolated arithmetic datapaths, not full accelerator subsystems with local memories and buffers. In fact, since this work involved the construction of a first release of the TCU accelerator, for simplicity the embedded DPUs are fully combinatorial and there is no pipeline mechanism at the DPU level.

Lastly, the Table indicates that in each DPU the format there is a number of FFs contributing to the area of each DPU. This is because during the synthesis of each DPU, there are included registers for its input operand elements and one register for the result. whose size vary depending on the expected bit width of the singular DPU. The inclusion of the registers at the input and output interface of the DPUs was necessary for the obtaining of performance related metrics for the DPU which is described more in detail in the subsequent section.

\section{DPU Level Timing Analysis}

%goal of this section is to answer how fast can each DPU implementation run after syntheis ? Which numerical formats create longer critical paths ? Why is that ? 

The timing analysis is equally as important as the resource analysis given in the last section. This is because optimally, the TCU accelerator circuit is integrated inside environments which are almost always synchronous such as the FlexGrip Plus GPU or the Klessydra T13 core which this thesis focused on. So, even though the focus of this thesis gave priority in the functional behavior of the integrated parametric TCU at simulation level, it was still important to provide the performance related metrics of this first relase of the unit to some extent in order to understand what there is to improve for future versions. Also, this analysis is important to be done at the DPU granular level to find out the differences in the performance related metrics among the various implemented DPUs each utilizing a different numerical format of operands. 

%Paragraph 5: Introduce the timing/Fmax metrics and the results data in general.

For studying the timing analysis and performance between the different DPUs inside the TCU, various related performance metrics have been focused which are the following ones: 

\begin{itemize}

    \item \textbf{Critical Path}: the longest combinationl path possible between the input registers and result register of a specific synthesized DPU relating to a specific numerical format.
    
    \item \textbf{Worst Negative Slack (WNS)}:  the metric portraying whether the design meets the synthesis constraints related to a selected clock frequency. If it is negative, the DPU design does not meet the clock constraints.
    
    \item \textbf{Estimated Maximum Frequency (Fmax)}: the approximate maximum clock frequency the design could reach.

\end{itemize}

Also it is important to remark that the synthesis flow used a target clock period of 10 ns. From the previously introduced table, it can be analyzed that out of all the first versions of the DPUs of the numerical formats, only the DPU which takes INT8 related operands respects the imposed clock constraint of 10 ns. Consequently, it makes sense that the similar DPU targeting INT16 operands is almost respecting the constraint with a slack of only -1.206 ns. The Fixed Point related DPUs are the next fastest DPUs after the integer related DPUs both with a slack less  -10 nanoseconds and are also much faster with respect to the DPUs which target the Posit, the Floating Point and the LNS formats. From the Table it can be observed in fact that the Floating Point and Posit formats have much longer critical paths. Specifically the 32 bit variants of these formats are the slowest out of all the othe DPUs and this is because they contain wider datapaths which consequently increase the complexity of the embedded arithmetic operations  circuits inside the DPU.

Another interesting result is shown when confronting the WNS slack between the Posit8 and FP8 format, the Posit16 and FP16 format, and the Posit32 and FP32 format. When confronting the WNS values between the pairs it can be seen that they are very similar with each other (for instance the Posit 8 DPU has a WNS of -64.568 ns compared to the WNS of -64.029 ns related to the FP8 DPU ). When also considering , as explained in chapter 3, that the floating point DPUs have a different structure (Early Accumulate structure) with respect to the organization of the posit related DPUs (Tree Adder structure), this result shows that independent of the methodology of the DPU design, the critical path delay between these two formats is comparable metric. With regards to the LNS16 DPU, the Table proves that it is slower than fixed/integer format DPUs, but comparable to 8 bit Posit and Floating Point ones.

%explaining WHy the results are the ones obtained. discussing a little basically. 

The Floating-Point and Posit implementations show significantly longer critical paths, especially for the 32-bit variants. This can be related to the larger datapath width and to the additional logic required for decoding, alignment, normalization, rounding, or regime handling. LNS16 also shows a relatively long critical path, which is mainly associated with the cost of logarithmic addition and subtraction. 

Since these values are obtained from post-synthesis timing reports, they should be interpreted as comparative estimates rather than final placed-and-routed operating frequencies. Nevertheless, because all DPU variants were evaluated with the same synthesis setup, the results provide a useful indication of the relative timing cost of each numerical format.

\section{DPU Level Numerical Accuracy Evaluation}

%this section will answer how accurate is each format for the same DPU operation.

%section will explain how numerical error was measured, show the results, comment on the main trends, then move to fault injection.

This section shows the results which have been obtained after the validation tests for each of the implemented DPUs. To obtain so, for each DPU related to the numerical formats a test flow has been applied involving the generation of 10000 dot product unit random operations which avoid overflow, the simulation of all the tests for the singular DPU, and the confrontation between the best expected result with respect to the one obtained from simulation. The range of the operands is kept the same in between simulations of the various DPUs. In this functional verification step the focus doesnt serve to obtain a correctness study for the format, but also to obtain the quantitative comparison of numerical behavior across the formats of each DPU. 

Like explained in the background chapter of this work, the operation done by each of the DPUs is the following one: \begin{equation}
R = A_0B_0 + A_1B_1 + A_2B_2 + A_3B_3 + C_0
\end{equation} Furthermore the tested 10000 vectors contain values which are the typical ones found in DNN random vectors. The vectors were generated using the same flow described in the DPU error-analysis scripts in chapter 2. 

Regarding the reference result values for each of the tests for each of the formats, they rapresent the ideal full-precision real result calculated by the same Python script which also calculated the random test vectors for the testbench. Basically, for each format a Python script computes the full-precision reference test, then each of the generated operands are quantized into the target format. Then, the VHDL DPU computes the encoded result through simulation and that output is decoded back into a real value (always by means of a Python script) in order for the comparison to the expected result to be done. Finally for each format DPU, by means of comparison Python script, the decoded DPU result obtained in simulation is compared against the full-precision reference whose output is to be used for obtaining the error related metrics of the DPUs. 

Like the results related to the hardware area and timing alysis explained in the previous sections of this chapter, the results obtained forming the numerical accuracy evaluation of each DPU regard various related metrics which involve the following, always obtained for each of the format related DPUs: 
\begin{itemize}
    \item \textbf{Number of tests}: total number of input vectors used for the
    evaluation. In this experiment, each format was evaluated using 10,000 DNN-like random test vectors.

    \item \textbf{Exact-match percentage}: percentage of test cases for which
    the decoded DPU output exactly matches the corresponding reference result. This metric is especially meaningful for integer-domain formats related DPU, where a 100\% exact match indicates that the expected integer arithmetic was reproduced for all tested vectors.

    \item \textbf{Mean absolute error}: average absolute difference between
    the reference result and the decoded hardware result. This metric provides a general indication of the average numerical deviation introduced by the format and by the DPU arithmetic.

    \item \textbf{Maximum absolute error}: largest absolute difference observed over the full set of test vectors. This metric highlights the worst-case deviation found during the experiment.

    \item \textbf{Root mean square error (RMSE)}: quadratic error metric that gives
    more weight to larger deviations. It is useful to compare the overall numerical behavior of the different real-valued formats.

\end{itemize}

For the real-valued formats, the absolute error, relative error, and RMSE are expressed in decoded real-value units. For the integer-domain formats, the corresponding error metrics are expressed in integer counts. For this reason, the integer-domain results are used mainly to verify arithmetic correctness and should not be interpreted in the same way as the real-valued error results.

After the Vivado simulation for each of the DPUs for each of the numerical formats, the related accuracy related errors have been collected in Table~\ref{tab:dpu_numerical_accuracy}. The values of the metrics reported in the table are the ones corresponding to operands which are in the range -1 to 1 for all the formats which rapresent values in the Real domain. This is done to omit overflow and hence compare the accuracy of each particular DPU more precisly with one another.

Observing the Table, it can be remarked that the results yield that 32-bit real-valued formats produce the lowest error. Specifically, the Posit32 format has the lowest mean absolute and RMSE among all the formats in the dataset. FP32 DPU is the next best solution with errors in the range of the nano scale magnitude. Regarding the operands with width of 16 bits, the DPU supporting the Posit16 format shows lower mean absolute error as well as lower RMSE with respect to the standard FP16, LNS16, and Fixed Point 16 counterparts. Regarding the DPUs treating with formats of the smallest width, FP8 and Posit8 DPUs show the largest errors as expected due to their reduced bit-width size. Also Obeserving the table it can be observed that the lower are the amounts of bits used for the result of the format the higher is the exact match percentage case however by just a small percentage case of variation. The error related metrics have also been plotted for all the 10000 tests into different seperate plots which portray the expected resulting value of each of the singular 10000 test versus the absolute error calculated from the simulated result of the DPU. These plots were usefull to understand the presence of outliers and other phenomenons and were also useful to compare the different DPU's obtained errors according on the format. For example,the Figure~\ref{fig:dpu_error_metrics_comparison} shows the plots reported for the confronting the errors of the 10000 tests of the Floating Point format DPUs against the Posit format related DPUs, and it can be observed also through these plots the difference in the magnitude of the error, where the Posit related DPUs result in a lower error with respect to the Floating Point ones.

When discussing more about the related numerical accuracy results just provided in this section, the Posit formats over all show lower mean absolute error and RMSE than the corresponding floating-point formats in this experiment. This behavior can be related to the tapered-precision property of Posit arithmetic, which allocates precision differently from conventional Floating-Point formats and can be particularly effective for values concentrated around a limited numerical range. But as a tradeoff of this when the range of the operand increases however, the behavior of the absolute area of the posit format will get closer to the numerical format of Floating Point. Regarding the other emerging format of LNS16,  even if the multiplications part of the dot product operation are convenient in LNS format, the DPU still needs several additions/accumulations part of the operation. And as a result of this, this is where the LNS16 related error metrics increase with respect to the floating point and posit related formats shown in the previously introduced table. In general,  this explains why LNS16 format is less accurate than FP16 and Posit16 in this experiment, while still remaining more accurate than the evaluated 8-bit formats due to the presence of more precision bits in that case. Lastly, for motivating the numerical format of Fixed Point, it can be remarked that since Fixed-Point arithmetic uses a uniform quantization step, it cannot adapt its precision to the magnitude of the represented values as floating-point or posit formats do. As expected, FXP16 significantly reduces the error with respect to FXP8 due to the larger input and output precision. However, in this dataset, FXP16 remains less accurate than FP16 and Posit16, suggesting that the selected fixed-point scaling provides a simpler but less flexible approximation of the real-valued dot product.

\section{DPU-Level Resiliency Analysis}

Along with the analysis described in the previous sections, there is also the resiliency associated study of the various DPUs. This resiliency is also very fundamental for one of the objectives of the thesis which is that of finding out the resiliency characteristics of each of the formats of the accelerator implemented in this work. The resiliency in this work has been studied through the sensitivity analysis of each of the real value implemented DPUs to permanent stuck at faults of the input signals of each DPU. In fact for each of the specific format DPUs, faults have been injected at the input interface of the component before begining a related simulation flow through Vivado. More specifically the resulting resiliency behavior has been investigated through the many comparisons of the faulty result due to the faults with respect to the fault free result. In this work, the resiliency analysis has been done in the embedded DPUs of the TCU accelerator rather then the overall TCU principally due to timing constraints, as the fault campaigns involving the TCU and its surrounding environment takes many more time with respect to the fault campaign done with respect to the individual format specific DPUs. But nonetheless, injecting faults in the various specific formats is a beggining approach of the resiliency evaluation giving usefull distinguishment of resiliency of the various numerical format DPUs implemented in this work. Furthermore, the results characterize the sensitivity of the implemented DPU input datapaths and should not be interpreted as a complete gate-level reliability analysis of the entire TCU.

%describing the shared workload. 

Regarding the specific methodology of the fault injection flow related to each of the different numerical supportive DPUs, the fault campaign flow involves 100 vectors of 9 operands of the format specific DPU targeted where each operand is in the range of -1 to 1 to avoid the overflow scenarios when testing all the formats and for mantaining test coherency. The decoded values of the 100 vectors of the campaign are the same for all the DPUs, the encodings however differ depending on the DPU targeted. Each faulty result obtained in simulation was compared with the fault-free golden output generated by the same DPU format and the same input vector.

%Fault model

With regard to the adopted fault model, as already introduced at the
beginning of this section, permanent stuck-at faults were considered.
For the resiliency evaluation of each DPU, the effects of applying
stuck-at-0 and stuck-at-1 faults to the input bits of the operand lines
were simulated individually.

A fault was classified as not activated when the forced value was equal
to the original value of the selected bit. Conversely, when the forced
value differed from the original bit, the fault was considered
activated. The activated faults were subsequently divided into two
classes:

\begin{itemize}
    \item \textbf{Masked}: the faulty encoded output was identical to
    the corresponding fault-free golden output;

    \item \textbf{Silent Data Corruption (SDC)}: the faulty encoded
    output differed from the corresponding fault-free golden output.
\end{itemize}

The number of injectable bits contained in one operand vector depends on
the widths of the nine DPU input operands. Let $w_j$ denote the width of
the $j$-th operand. The total number of injectable bits per vector is
therefore defined as

\begin{equation}
N_{\mathrm{bits}}
=
\sum_{j=1}^{9} w_j .
\label{eq:dpu_injectable_bits}
\end{equation}

For DPU variants in which all nine operands have the same width $w$,
Equation~\ref{eq:dpu_injectable_bits} reduces to
$N_{\mathrm{bits}}=9w$. For the mixed-width fixed-point variants, the
actual width of each operand was considered separately.

Since both stuck-at-0 and stuck-at-1 conditions were applied to every
injectable bit of every vector, the total number of simulated fault
cases is given by

\begin{equation}
N_{\mathrm{cases}}
=
2 N_{\mathrm{vectors}} N_{\mathrm{bits}},
\label{eq:dpu_total_fault_cases}
\end{equation}

where the factor 2 accounts for the two stuck-at conditions (stuck at 0 and stuck at 1). Since one of the two forced values preserves the original bit and the other changes it, the number of activated faults is

\begin{equation}
N_{\mathrm{activated}}
=
N_{\mathrm{vectors}} N_{\mathrm{bits}}.
\label{eq:dpu_activated_faults}
\end{equation}

For the comparison of the resiliency results among the different
numerical-format-specific DPUs, the activated SDC rate was used as the
main evaluation metric. It is defined as

\begin{equation}
\mathrm{SDC}_{\mathrm{activated}}
=
\frac{N_{\mathrm{SDC}}}
{N_{\mathrm{SDC}}+N_{\mathrm{masked}}}
\times 100,
\label{eq:dpu_activated_sdc_rate}
\end{equation}

where
$N_{\mathrm{SDC}}+N_{\mathrm{masked}}=N_{\mathrm{activated}}$.
Therefore, Equation~\ref{eq:dpu_activated_sdc_rate} expresses the
percentage of the faults that actually modified an input bit and
subsequently produced an output different from the corresponding golden
result.

So with the help of the mentioned formulas and methedology, for FP8 and Posit8 format DPUs 14,400 total cases have been studied 7,200 activated faults. For FP16 , Posit16 and LNS16 28,800 total cases have been analyzied 14,400 of which are activated faults, and for FP32 and Posit32 DPUs 57,600 total cases have been studied in simulation each of where 28,800 are activated faults. For the width DPU width DPU of FixedPoint8 operands but with result on 16 bits, 16,000 total cases have been studied where 8,000 of them are activated faults. While for FixedPoint16 operand DPU 32,000 total fault cases aroise where 16,000 of them are activated faults. Since the number of injectable bits and consequently the number of fault cases differ among the formats, the comparison is mainly based on the activated SDC rate rather than on the absolute SDC count.

Furthermore, neither Floating Point nor Posit showed uniform superiority across all widths. Also, with regards to the FIxed Point and LNS format DPU's resiliency, LNS16 format DPU has a lower SDC rate than FP16, Posit16 and Fixed Point 16. Moreover, in the FXP16/32 campaign, none of the multiplicative operands was quantized to zero, allowing every activated input fault to propagate to the result.

Many important observations and analysis with respect to the formats can be made when analyzing the boxplot.  Regarding the FP8 and Posit8 DPUs, they present the widest distributions among the evaluated formats. FP8 has the lowest mean activated SDC rate, but also the greatest variability across the 100 vectors. Posit8 also shows a very broad distribution, although its central SDC rate is higher than that of FP8. The interpretation for these resiliancy related distribution results suggests that the fault-masking capability of the 8-bit formats depends strongly on the particular operand values being processed. The reason is because the reduced precision of the 8-bit representations can cause some fault induced perturbations to be removed by rounding or quantization, but whether this masking occurs depends on the encoded values of the test of the input vector applied. 

With regards to the formats composed of 16 bit widths, they show even narrower distribution compared to the previously analyzed 8-bit formats. FP16 and Posit16 have the same average activated SDC rate, but the Posit16 box is slightly narrower. Even though the average sensitivity is the same, the Posit16 related format DPU behaves a little more consistently across the 100 vectors. For the mixed width FXP16/32 format, the activated SDC rate was equal to 100\% for all the tested vectors. This means that every activated fault changed the output compared to the golden result. In conclusion for the resiliency analysis, in this work faults have been injected at the DPU input interface. With those campaigns, SDC classification has been extracted for each of the DPU specific formats and the classification was based on exact output comparison with respect to a golden simulation for each vector in a fault campaign. It has been observed a very small difference and a large error were both counted as SDC. Lastly, the resiliency result conclusions are valid for the selected 100 vectos and adopted stuck at fault model in this work, hence but not universally for every workload and based on the campaign's results it has been observed that lower-width formats showed more masking but also more dependence on the input vectors, while higher-width and fixed-point formats showed higher and more consistent exact-output sensitivity.

\section{Summary}

This chapter presented the experimental evaluation of the different
DPU implementations and of the parametric TCU integrated inside the
FlexGrip Plus and Klessydra T13 environments. The comparison was done
considering hardware utilization, timing, numerical accuracy and
resiliency. The synthesis results showed that the Integer and
Fixed-Point DPUs are generally the cheapest and fastest solutions,
while the Floating-Point, Posit and LNS implementations require more
hardware resources and present longer critical paths. In particular,
the 32-bit Floating-Point and Posit variants resulted among the most
hardware-expensive implementations, while the LNS16 DPU also required
a high number of LUTs because of the complexity of its logarithmic
addition operations.

The numerical accuracy analysis showed that the higher-width formats
produce lower errors, with Posit formats obtaining lower mean absolute
error and RMSE than the corresponding Floating-Point formats for the
selected dataset. The Integer DPUs reproduced the expected results for
all the tested vectors. The fault campaigns also showed that lower-width formats provide more fault
masking, but their behavior depends more strongly on the applied input
vectors. Instead, the higher-width and Fixed-Point formats presented
higher and more consistent SDC rates.

Finally, the TCU-level analysis showed that the FlexGrip Plus
dual-TCU wrapper requires approximately twice the LUT resources of the
single Klessydra TCU wrapper. The HMMA Step~0 instruction is also
executed in fewer clock cycles in FlexGrip Plus, mainly because the GPU
threads can load the TCU inputs in parallel, while the Klessydra harts
perform the operand collection in a round-robin manner. These results provide the main
experimental observations of the implemented accelerator and also
highlight the aspects that should be improved and studied in future
work.
